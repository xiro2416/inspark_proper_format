# RTX 4090 / SM89 deployment

This port keeps the upstream SM120 release and its measured plan files intact.
SM120 plans are not loaded on SM89. All commands below expose exactly one
physical GPU and do not perform online autotuning.

## Profiles

- `configs/sm89_fp32.json`: correctness baseline.
- `configs/sm89_bf16.json`: BF16 cuBLAS/cuDNN baseline.
- `configs/sm89_bf16_triton.json`: BF16 baseline plus the validated CFM
  RMSNorm/modulation and QKV+RoPE Triton fusions.

The Triton profile deliberately excludes the existing SiLU+gate fusion. On the
local RTX 4090 it was slower than eager PyTorch at the representative shape.
It also excludes FP8 GEMM and Target LayerNorm+FP8 quantization: both candidates
were numerically valid but slower than their BF16/separate-operation controls.

## Reproduce

Use a physical GPU index in each command:

```bash
CUDA_VISIBLE_DEVICES=3 bash scripts/run.sh scripts/preflight_sm89.py \
  --deployment configs/sm89_bf16_triton.json

bash scripts/run.sh scripts/benchmark_sm89_fusions.py --gpu 3
bash scripts/run.sh scripts/benchmark_sm89_gemm.py --gpu 3
bash scripts/run.sh scripts/benchmark_sm89_norm_quant.py --gpu 3
bash scripts/run.sh scripts/benchmark_sm89_batch.py --gpu 3 --batch 8 \
  --ref-audio /path/to/reference.wav

INSPARK_GPU=3 bash scripts/smoke_test_sm89.sh /path/to/reference.wav bf16-triton
```

## Local RTX 4090 evidence

Software identity: PyTorch 2.8.0+cu128 and Triton 3.5.0. These are microbenchmarks,
not portable performance claims.

| Candidate | Representative result | Decision |
| --- | ---: | --- |
| CFM RMS fusion | 2.69x microbenchmark speedup | enable |
| CFM QKV+RoPE fusion | 6.77x microbenchmark speedup | enable |
| CFM SiLU+gate fusion | 0.75x | reject |
| BF16 cuBLAS GEMM | 22.9-27.4 us | retain |
| `torch._scaled_mm` prequantized | 48.5-60.0 us | reject |
| `torch._scaled_mm` with dynamic quantization | 70.0-87.4 us | reject |
| prequantized Triton W8A8 GEMM | 30.7-31.4 us | reject |
| dynamic Triton quantize+GEMM wrapper | 75.5-78.2 us | reject |
| Triton LayerNorm+FP8 quantize fusion | 0.85-0.86x | reject |

For the fixed smoke input, BF16+Triton produced 49,152 samples exactly equal to
the BF16 baseline PCM. The observed one-shot request times were 115.8 ms first
packet / 552.6 ms total versus 117.8 ms / 565.6 ms for BF16. The first packet
contained 11,264 samples, preserving the 44 acoustic-frame contract.

## Concurrent first-chunk benchmark

The batch benchmark admits the requested number of sessions concurrently and
keeps scheduling until every session has received its first chunk. Values below
are three post-warmup runs on physical GPU 3. Power is instantaneous whole-board
power reported by NVIDIA; the documented sensor accuracy is approximately
`+/-5 W`, and sub-second B1 readings have limited temporal resolution.

| Batch | Head graphs | First request | All requests ready (mean) | Board power | Result |
| ---: | :---: | ---: | ---: | ---: | --- |
| 1 | yes | 79.1-84.3 ms | 81.0 ms | about 99.5 W | pass |
| 8 | yes | 90.7-110.1 ms | 251.1 ms | about 200.9 W steady, 201.4 W peak | pass |
| 16 | yes | 137.6-151.8 ms | 361.4 ms | about 203 W steady/peak | pass |
| 32 | yes | n/a | n/a | n/a | OOM during BigVGAN head-graph capture |
| 32 | no | 220.5-248.8 ms | 897.3 ms | 164.0 W window mean, 189.6 W peak | fallback pass |

Every successful request produced an 11,264-sample first chunk. Batch 32 with
the normal all-graph profile is not deployable on this 48 GB device: it used
47.31 GiB and failed a further 40 MiB allocation even with no reservation
process present. The no-head-graph row is a capacity fallback, not directly
comparable to the graph-enabled rows.

### GPU 6 barrier throughput and power

With `head_batch_barrier=true`, two warmups followed by ten recorded runs on an
otherwise idle physical GPU 6 produced the following first-chunk batch results.
Throughput is `requests / time until every request has its first chunk`; every
event reported the requested real CFM/Vocoder batch and 11,264 samples.

| Batch | Mean all-ready | Range | Throughput | Aggregate audio rate | Mean board power | Peak board power |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 174.1 ms | 159.7-195.7 ms | 46.07 requests/s | 23.53 audio-seconds/s | about 209.8 W | 270.6 W |
| 16 | 418.3 ms | 409.5-423.2 ms | 38.26 requests/s | 19.54 audio-seconds/s | about 209.5 W | 329.2 W |

The NVIDIA instantaneous-power sensor updates more slowly than an individual
174-418 ms run, so the power values are whole-board approximations rather than
per-module measurements. The latency and throughput measurements were stable
enough to show that B8 is the better first-chunk throughput point for this
barrier-enabled profile; doubling admission to B16 reduced throughput by about
16.95% while increasing all-ready latency by about 2.40x.

## Safety boundary

`src/inspark_infer/ops/triton/target_norm_quant/triton_fused.py` is retained as an
offline experiment. It is not wired into a deployment profile. The existing
CUDA implementation in the same package is hard-coded to SM120 and must not be
built or loaded for this SM89 profile.
